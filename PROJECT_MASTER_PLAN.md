  Bloodborne PSX Demake, тикток-эстетика «PS1 dark fantasy» (аллея к замку под зелёной луной)
- **Команда:** я (соло, полный новичок) + ты (ИИ-ассистент)
- **Платформа:** PC (Windows), цель — Steam. Промежуточная веха: бесплатная демка на itch.io
- **Сроки (реалистичные, при 15+ ч/нед):** вайб-скрин — к концу недели 3; демка 15–30 мин —

# ART DIRECTION — PS1 DARK FANTASY (не обсуждается)

## Канон рендера
- Рендер в низком разрешении: SubViewport **480×270** (запасной вариант 320×240),
  растягивание на весь экран с nearest-фильтрацией — картинка «пикселится»
- **PSX-шейдер** на всех материалах: vertex snapping (дрожание геометрии),
  affine texture mapping (плывущие текстуры), дизеринг, сглаженная палитра
- **Туман:** экспоненциальный, тёмный сине-фиолетовый, дальность видимости ~15–40 м
- **Небо:** процедурный шейдер (градиент ночи + звёзды + зелёная туманность).
  БЕЗ HDRI, БЕЗ скайбоксов с дневным небом
- **Луна:** огромная, бледно-зелёная, Sprite3D с эмиссией, видна почти из любой точки
- **Свет:** холодный слабый DirectionalLight (луна, синий) + тёплые точечные источники
  (окна замка, костры, фонари) — контраст «холод снаружи / тепло в густо»
- **Постобработка:** плёночное зерно, виньетка, лёгкая хроматическая аберрация по краям

## Лимиты (проверяются на каждой задаче)
- Текстуры в игре: **128–256 px**, nearest-фильтрация. Никаких 2K/4K
- Модели: декор ≤ 2 000 трис, важный проп ≤ 5 000, герой ≤ 10 000
- FPS: ≥ 60 на среднем ПК
- Палитра: глубокие сине-фиолетовые ночи, зелёный акцент луны и магии, тёплый оранжевый
  огня. Запрещены: яркая дневная зелень, чистые белые поверхности, «солнечные» текстуры

## 2. GDScript — строгая типизация

- ВСЕ переменные, параметры и возвращаемые значения типизированы:
  `var hp: int = 100`, `func take_damage(amount: int) -> void:`
- `@export` — для всего, что настраивается в Инспекторе; `@onready` — для ссылок на ноды
- Файл ≤ 300 строк, функция ≤ 40 строк. Превышение — предложить разбиение
- `##` doc-комментарий над каждым публичным методом и `class_name`
- Конвенции: файлы/переменные `snake_case`, классы/ноды `PascalCase`, константы `CONST_CASE`
- Только синтаксис Godot 4. Запрещено: `onready var`, `yield`, `instance()`,
  `OS.get_ticks_ms()`, `.connect()` строковыми именами методов

## 3. Связи и зависимости

- Вниз по дереву сцены — прямые ссылки (`$Child`); вверх и между сценами — ТОЛЬКО сигналы
- UI никогда не обращается к игроку/врагам напрямую — слушает EventBus
- Автолоады: максимум 5 (EventBus, GameState, AudioManager, SaveSystem).
  Новый autoload — только после явного согласования с партнёром
- Балансные числа (урон, HP, скорость, дальность) — НИКОГДА не хардкодить:
  `@export` или поля в Resource из `data/`
- Данные: `class_name EnemyData extends Resource`, экземпляры — `.tres` файлы
- Компоненты вместо наследования скриптов: HealthComponent, HitboxComponent,
  StateMachine — отдельные ноды внутри сцены
- Запрещено: абсолютные пути `get_node("/root/...")`, `find_child()` вне локальной сцены,
  растущие цепочки if/else вместо FSM

## 4. Специфика 3D и рендера

- Логика отдельно от визуала: корень — CharacterBody3D / Area3D / Node3D,
  MeshInstance3D — дочерняя нода
- Анимации: AnimationTree с конечным автоматом; переключение — из скриптов состояний
- Матрица слоёв коллизий (layer/mask) ведётся таблицей в `docs/collision_matrix.md` — не отступать
- ИИ врагов: NavigationAgent3D + FSM состояний (patrol/chase/attack/hurt/die)
- Камера — отдельная сцена-компонент (SpringArm3D), ввод через Input Actions
- PS1-пайплайн — часть ядра: сцена рендерится в SubViewport 480×270, PSX-шейдер
  подключается всем материалам через общий ShaderMaterial-пресет в `assets/materials/`

## 5. Производительность — с первого дня

- `_physics_process` — физика и движение; `_process` — только камера/кадровый ввод
- Никаких `get_tree().get_nodes_in_group()` в кадре — кэшировать ссылки
- Таймеры (Timer/SceneTreeTimer) вместо счётчиков времени в `_process`
- Рейкасты — экономно, результаты кэшировать

# ПРАВИЛА НАШЕЙ РАБОТЫ (workflow)

1. Одна итерация = одна задача. Файлы вне задачи не трогать
2. Формат каждого ответа с кодом:
   а) список файлов, которые будут изменены/созданы
   б) ПОЛНЫЙ код каждого файла целиком (не диффы, не «добавь после строки...»)
   в) 2–3 предложения: что сделано и почему именно так
   г) чеклист ручной проверки: что партнёру запустить/настроить/кликнуть в редакторе
3. Инструкции для редактора Godot — пошагово, для человека, который видит его впервые
4. Задача двусмысленна — сначала 1–3 уточняющих вопроса, потом код
5. Выбор архитектуры — рекомендация по умолчанию с объяснением; альтернативы только
   если реально жизнеспособны; финальное слово за партнёром
6. Партнёр приносит ошибку: полный текст из консоли + полный код файла. Чинить точечно,
   несвязанное не переписывать
7. После каждой закрытой задачи — текст для git-коммита
8. Работающий код без просьбы «не улучшать» — регрессии важнее стиля
9. Партнёр может прислать старый код как контекст — считать его актуальным состоянием
